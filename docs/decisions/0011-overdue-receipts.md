# 지연 발주 상태와 계산 입력 (#91, BE-07)

상태: 2026-11-06 사용자 승인. 서울 오늘 기준 권장안을 사용한다.
대상: R1 목록, R2 등록 응답, R3 수정 응답, 새 계산의 plannedReceipts.

## 정책

| 조건 | 응답 status | reflected | 새 계산 |
|---|---|---|---|
| 입고 매칭 완료 | RECEIVED | false | 제외 |
| 취소 | 목록에서 제외 | false | 제외 |
| 예정일 없음 | NO_DATE | false | 수량 제외, 기존 설명용 noDateReceipts 유지 |
| 예정일 < Asia/Seoul 오늘 | OVERDUE | false | 제외 |
| 예정일 = 오늘 또는 미래 | PENDING | true | 기존 asOfDate 초과 조건과 상품 선택 조건을 만족하면 포함 |

예정일 전/당일은 지연으로 보지 않는다. 오늘은 Clock에서 요청 시 읽고 날짜 판정은 엔티티의 공통 함수로 수행한다. 등록·수정은 창고 잠금 뒤 업무일을 한 번 고정해 응답과 계산 snapshot이 자정을 걸쳐도 일치시킨다. 상태가 저장된 OVERDUE라도 예정일을 오늘/미래로 고치면 다시 PENDING 후보가 된다. 입고 완료·취소가 날짜 판정보다 우선하며, NO_DATE의 날짜를 나중에 입력하면 같은 규칙으로 판정한다.

수불부가 10/31, 서울 오늘이 11/6일 때 미입고 11/3 예정 발주는 OVERDUE로 계산에서 제외한다. 수불부 기준일만 사용하는 대안은 미입고를 도착 물량처럼 계속 포함할 수 있어 채택하지 않았다. 오늘 예정 물량을 유지하는 것은 사용자 승인 정책이며 실제 당일 입고를 보증하지 않는다.

## 저장·계산 경계

- 지연은 날짜로 파생되는 상태다. GET은 DB 상태·updated_at을 쓰지 않는다. 신규 migration/cron/스케줄러가 없다.
- 기존 DB의 PENDING/OVERDUE는 #90의 입고 매칭 후보로 유지한다. RECEIVED 전환은 검산된 실제 입고 매칭으로만 수행한다. 완료 발주 수정/취소 409와 창고 잠금은 유지한다.
- 날짜 경과로 기존 DONE/QUEUED snapshot을 바꾸지 않는다. 기존 화면의 계산 결과는 생성 당시 결과다. 새 계산 요청에서 새로운 today와 필터가 입력 hash에 반영된다.
- 목록은 다음 조회, 계산은 다음 업로드·설정/발주 변경·명시적 재계산에 반영된다. 자정 자동 재계산이나 화면 자동 재조회 기능을 추가하지 않는다.
- reflected는 날짜상 후보 여부다. 비활성 상품·검산 제외·설정 미확정·자료 부재 및 asOfDate 이하 제외까지 모두 통과했다는 의미가 아니다. 실제 생성/재사용은 runId, 결과는 C2로 확인한다.
- JSON 필드·기존 상태값·HTTP code와 헤더 계약은 유지한다. Client는 이미 OVERDUE 표시를 지원하므로 이번 변경은 서버에 한정한다. 실제 배포 화면은 별도 검증이다.

## 검증과 복구

고정 Clock의 서울 자정 전/후, 과거/당일/미래, 날짜 없음→날짜 입력, 예정일 변경, 취소/입고 완료 우선순위와 보호를 검사한다. 실제 Spring/H2의 계산 outbox 입력에서 과거 발주 제외·당일/미래 포함·변경/취소 뒤 새 run과 과거 snapshot 불변을 대조한다. 기존 #90 매칭 회귀를 함께 실행한다. 합성 fixture이며 실제 AWS/SQS/AI·고객 업무 효과 검증은 아니다.

스키마/기존 업무 행을 바꾸지 않아 이전 앱 코드로 되돌릴 수 있다. 이전 앱은 과거 예정 발주를 다시 계산 후보로 삼을 수 있으므로 정책 변경 영향은 남는다. 배포·DB 수정·과거 run 재계산은 별도 승인 범위다.
